Dos secuencias, separadas a propósito

edit (Flujo A, disparado por el caller) y ensure-closed (Flujo A', disparado también por el caller pero resuelto internamente por la skill) usan el mismo mecanismo de edición del markup por debajo, pero solo una de las dos puede tocar el estado de una nota.

✓ Regla: solo ensure-closed lee, resuelve y cierra notas. edit nunca las toca.
Caller → skill · Flujo A
action: edit
  • 1
    pv-new quiere agrandar un botón del mockup — pide action: edit a la skill de mockups.
  • 2
    La skill localiza el archivo, comprueba si ya tiene el framework de anotaciones embebido.
  • 3
    Edita solo el markup propio del mockup (el botón). nunca toca #mnote-data
  • 4
    Devuelve la ruta del archivo editado. Fin.
open "hacer este botón más grande" — sigue open, el edit no la vio
Aunque el edit casualmente resuelve lo que la nota pedía, la nota no se cierra aquí. El caller tendría que invocar ensure-closed aparte para que quede reflejado.
Caller → skill · Flujo A'
action: ensure-closed
  • 1
    pv-new, antes de volver a presentar el mockup, pide action: ensure-closed sobre ese design_*.html.
  • 2
    La skill lee #mnote-data internamente — el caller nunca la ve.
  • 3
    Encuentra la nota open "hacer este botón más grande". La aplica ella misma al markup (mismo mecanismo que un edit interno).
  • 4
    Marca la nota closed. nunca se borra — queda como registro.
  • 5
    Devuelve OK + resumen en texto plano ("agrandé el botón X"). Sin selectores, sin JSON.
closed "hacer este botón más grande" — resuelta por la skill
Si la nota fuera ambigua (p. ej. "arregla esto"), la skill pregunta directamente al usuario en este mismo paso, antes de aplicar nada — excepción única en todo el framework pv-internal-*.
por qué importa la separación
● caller invoca edit por su cuenta, cuando quiera → nunca resuelve ni cierra notas
● caller invoca ensure-closed antes de (re)presentar → única vía para leer, resolver y cerrar notas

Si un edit plano pudiera también cerrar notas "de paso", cualquier llamada normal de pv-new/pv-fix podría alterar #mnote-data sin que el caller lo supiera ni lo pidiera — rompiendo la regla de encapsulación que todo el plan defiende ("ningún caller lee, parsea o escribe #mnote-data").
