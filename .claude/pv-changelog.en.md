## ⭐New

- 📂**Per-skill workflow diagrams**:
  - **`pv-new` workflow diagram** — `pv-new` now ships a `workflow.new.md` diagram that is the source of truth for its flow (entry points, visual-representation cases, branching). The skill reads it before acting; the written steps are only per-node detail.
  - **`pv-fix` workflow diagram** — `pv-fix` now ships a `workflow.fix.md` diagram covering both the fast-track and the non-trivial sub-flows, read before acting.
  - **`pv-how` workflow diagram** — `pv-how` now ships a `workflow.how.md` diagram governing its sequence and branches, read before acting.
  - **`pv-version` workflow diagram** — `pv-version` now ships a `workflow.version.md` diagram driving its execution, distinct from the simplified user-facing diagram shown on request.
- **New shared skill for documentation file management** — a new internal skill, `pv-internal-doc-files`, centralizes how the three documentation folders (`architectureDocDir`, `styleBibleDocDir`, `featuresDocPathDir`) store files: numbering, slugging, `INDEX.md` regeneration, and the `find`/`upsert` actions. `pv-internal-doc-features` and `pv-do` delegate to it instead of each managing files their own way.
- **Initial code analysis reworked into a verified checklist** — when `pv-init` runs against a project that already has code, its documentation-generation step is now an explicit checklist: gather code context once (new `bootstrap` mode that skips path resolution while the folders are still empty placeholders), decide whether the project has a presentation layer, write the architecture docs, populate the namespace tree, draft the style bible only when there's a presentation layer, and build an exhaustive feature list (one entry per user-facing capability). Each item must be genuinely done and reported before initialization finishes.
- 📂**New framework-health checks in `pv-update`**:
  - **Missing or leftover configuration fields** — `pv-update` now flags any of the three documentation folders missing from `pv-context.json` (a broken state now that all three are required) and repairs it with the default path plus a scaffolded folder; it also removes keys a framework upgrade retired (such as `docs.tech.language`), including nested ones the generic unknown-field check couldn't reach.
  - **Namespace seed checks** — `pv-update` now verifies `architectureDocDir` has its `00-namespace.md` seed with the required `## Notation` and `## Tree` headings, and reports a namespace anchor whose target file no longer exists (asking the user rather than guessing the replacement).
- **Closing implemented entries in `pv.py` now loops** — the "close an implemented entry" option re-lists the remaining entries after each closure instead of returning to the menu, so several entries can be closed in one pass.

## ✏️Changed

- 📂**Documentation generation and structure**:
  - **The three documentation folders are now mandatory** — `architectureDocDir`, `styleBibleDocDir` and `featuresDocPathDir` are required fields in `schema.json`. `pv-init` always writes and scaffolds all three, and every skill refuses to run against a `pv-context.json` missing any of them, sending the user to `/pv-update`. A folder that exists but holds only its placeholder `INDEX.md` is fine — that just means nothing is documented there yet. **On update:** run `/pv-update` on any project initialized before this version; it adds the missing fields with their default paths and scaffolds the folders.
  - **Technical documentation is always English** — the `docs.tech.language` option has been removed. `architectureDocDir` and `styleBibleDocDir` content is now fixed technical English regardless of `interaction.language` or any other language setting, since it is written to be read by the skills themselves rather than by a person. Feature documentation, the changelog and in-progress change/fix documents keep their own language settings. **On update:** `/pv-update` removes a leftover `docs.tech.language` key and its `_comments` entry automatically.
  - **Architecture documentation gains a project namespace tree** — `architectureDocDir` now contains a single `00-namespace.md` file: one canonical dotted path per citable concept or assertion, with code anchors and a fixed notation for contracts and values. `pv-init` seeds it, `pv-do` keeps it in sync when a change adds or renames a citable concept, and style concepts hang off its `ui.*` branch (the style bible has no namespace file of its own). Documentation now cites concepts by their canonical path rather than re-describing them.
  - **Documentation files renumbered and given an area field** — files in the three documentation folders now use a 3-digit prefix (`001-`, `002-`…) instead of 2-digit, and each carries an `**Area**:` field that `INDEX.md` groups by — the same convention across architecture, style and features. `00-`-prefixed files are reserved infrastructure, excluded from the index and the numbering.
  - **Architecture documentation now follows a content checklist** — `pv-internal-doc-technical` no longer just supplies a writing style. When `pv-do` documents a change, it now returns which architecture content categories apply (components, contracts, data flows, decisions, dependencies, data model, configuration), which are already covered by the gathered context, and which are still pending — plus an expanded notation-first writing ruleset (contracts, state machines and structured data as notation rather than prose; `[gotcha]` and `[motivación]` tags; no anaphora; no unquantified intensifiers).
  - **Feature documentation skill now decides what and how to write** — `pv-internal-doc-features` now owns the domain rules for a feature entry: given a summary of what was implemented and the gathered context, it drafts the entry itself (functional description, which functional diagrams carry over, in-place edit vs. new entry) applying its own content checklist and human-facing writing rules, and delegates all file mechanics to `pv-internal-doc-files`. `pv-do` supplies the summary and context instead of pre-drafting the content.
- **Paths in `pv-context.json` are now resolved through a script** — skills no longer read the `docs.*` path fields out of `pv-context.json` directly. `pv-new`, `pv-fix`, `pv-how`, `pv-do` and `pv-internal-tech-analysis` obtain each documentation folder's absolute path from a new `resolve-path.py` helper, and stop with a `/pv-update` message if resolution fails. A path that resolves successfully is correct by definition, so `pv-internal-tech-analysis` no longer reports "your `docs.*` paths look misconfigured" as a documentation-vs-code inconsistency.
- **More structural markers in `description.md` and `plan.md`** — the always-present section headings in these templates (`## Full description`, `## (a) Functional notes`, `## (b) Technical solution`, `## (e) Verification`) are now marked to stay in English, alongside the field labels that were already marked. `pv-update`'s marker check now also scans `implemented/*/plan.md`, and recognises a heading left translated by an older framework version whose templates were still localized, restoring just the heading. **On update:** run `/pv-update`; it rewrites any translated heading in existing change/fix documents back to English without touching the content beneath it.
